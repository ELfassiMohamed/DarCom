 TASK 01 — Domain Entities (JPA)
--------------------------------------------------------------------------------
 Goal: Create the JPA domain model from API-Specification.md §3/§12/§13 as
       Hibernate-managed entities that generate the DDL via drop-and-create.

 Deliverable: 12 files — 7 entities + 5 enums. No repositories/services.

 Files created (src/main/java/com/backend/domain):
  1. domain/User.java                    @Table(users)
  2. domain/Listing.java                 @Table(listings)
  3. domain/Photo.java                   @Table(photos)
  4. domain/Booking.java                 @Table(bookings)
  5. domain/Message.java                 @Table(messages)
  6. domain/Report.java                  @Table(reports)
  7. domain/RefreshToken.java            @Table(refresh_tokens)
  8. domain/enums/UserRole.java          HOST, VISITOR, ADMIN
  9. domain/enums/ListingStatus.java     ACTIVE, HIDDEN, REMOVED
 10. domain/enums/BookingStatus.java     PENDING, CONFIRMED, REJECTED, CANCELLED + state machine
 11. domain/enums/ReportReason.java      SCAM, MISLEADING_LISTING, INAPPROPRIATE_BEHAVIOR, OTHER
 12. domain/enums/ReportStatus.java      OPEN, REVIEWED, DISMISSED, ACTIONED

 Global conventions (all 7 entities):
  - No inheritance/@MappedSuperclass (audit columns differ per table)
  - @Id @GeneratedValue(GENERATION.UUID) java.util.UUID, explicit @Column(name) snake_case
  - All @ManyToOne FetchType.LAZY, optional=false where FK NOT NULL
  - Only bidirectional: Listing.photos <-> Photo.listing (cascade ALL + orphanRemoval + @OrderBy sortOrder)
  - No Lombok, hand-written getters/setters, public no-arg ctor required by JPA
  - equals/hashCode: final, id-based (id!=null && id.equals(other.getId())), hash = Class.hashCode() (proxy-safe)
  - toString: scalar fields only (never association/collection, never passwordHash/tokenHash)
  - Timestamps: Instant (TIMESTAMPTZ) via @PrePersist/@PreUpdate, LocalDate for checkIn/checkOut
  - Enums: @Enumerated(STRING), never ORDINAL; Jakarta imports only

 Entity details:
  User: email(@Email @NotBlank unique 255), passwordHash(255), fullName(255), phone(30), role(UserRole 20),
        verified/blocked boolean, createdAt (TIMESTAMPTZ). No collections on User by design.
  Listing: host(User FK host_id), title(255), description(TEXT), city(120), address(255),
           pricePerNight(BigDecimal 10,2 @PositiveOrZero), currency(3 default MAD), mealsIncluded bool,
           activities @ElementCollection Set<String> -> listing_activities(listing_id, activity 120) LinkedHashSet,
           status(ListingStatus ACTIVE), photos List<Photo>, createdAt, updatedAt. Helpers addPhoto/removePhoto + clear-and-addAll setters.
  Photo: listing(FK listing_id), url(500 @NotBlank), sortOrder int 0. No timestamps.
  Booking: listing(FK), visitor(FK visitor_id), checkIn/checkOut LocalDate @NotNull, guestsCount int @Positive,
           status(BookingStatus PENDING), createdAt, updatedAt. No totalPrice/message fields. TODO checkOut>checkIn in service.
  Message: listing(FK), sender(FK sender_id), receiver(FK receiver_id), body(TEXT @NotBlank), sentAt(PrePersist), readAt.
           Threads derived via (listing_id, sender_id, receiver_id).
  Report: reporter(FK), reportedHost(FK reported_host_id), listing(FK nullable), reason(ReportReason 30),
          details(TEXT), status(ReportStatus OPEN), adminNotes(TEXT), createdAt, reviewedAt(admin action).
  RefreshToken: user(FK user_id), tokenHash(512 unique @NotBlank, stores hash never raw), expiresAt, createdAt,
                isExpired() = expiresAt < now, toString excludes hash.

 Companion changes:
  pom.xml: added jakarta.validation-api 3.0.2 (runtime, because jakarta.jakartaee-api is provided; same fix as persistence-api)
  persistence.xml (META-INF): added 7 explicit <class> entries for reliable discovery under RESOURCE_LOCAL/WAR (invest-pu retained)
  Drop-and-create retained: Hibernate rebuilds schema from annotations on each EMF start; data does not survive restart.

 Verification: mvn clean compile BUILD SUCCESS (13 src files with TestServlet), no FetchType.EAGER, no javax., no ORDINAL.

 1) persistence.JpaUtil  [src/main/java/com/backend/persistence/JpaUtil.java]
    Purpose: Single owner of EntityManagerFactory for whole app. Replaces inline
             Persistence.createEntityManagerFactory(...) from smoke checks.
             Uses Dotenv to inject DB_URL/DB_USER/DB_PASSWORD + driver.

    - private static final String PERSISTENCE_UNIT_NAME = "invest-pu"
      Constant matching persistence.xml persistence-unit name. Update in one place if renamed.

    - private static final EntityManagerFactory EMF = buildEntityManagerFactory()
      Eagerly built singleton, reused for all EntityManagers.

    - private JpaUtil() {}
      Prevent instantiation (utility class, final).

    - private static EntityManagerFactory buildEntityManagerFactory() : EntityManagerFactory
      Loads Dotenv.load(), builds Map<String,String> props:
        jakarta.persistence.jdbc.url      -> dotenv.get("DB_URL")
        jakarta.persistence.jdbc.user     -> dotenv.get("DB_USER")
        jakarta.persistence.jdbc.password -> dotenv.get("DB_PASSWORD")
        jakarta.persistence.jdbc.driver   -> "org.postgresql.Driver"
      Returns: Persistence.createEntityManagerFactory(PERSISTENCE_UNIT_NAME, props)

    - public static EntityManager createEntityManager() : EntityManager
      Delegates to EMF.createEntityManager(). Caller (currently manual, later Service) opens/closes transaction.

    - public static void shutdown() : void
      Closes EMF if open. Not yet wired; intended for ServletContextListener.contextDestroyed().

 2) repository.Pageable  [src/main/java/com/backend/repository/Pageable.java]
    Purpose: Typed pagination envelope. Every paginated repo method takes one
             Pageable instead of two raw ints. Validation here, size clamping (max 100) in Service/Resource.

    - public record Pageable(int page, int size)
      Compact record. Canonical constructor validates:
        if page < 0 throw IllegalArgumentException("page must be >= 0")
        if size < 1 throw IllegalArgumentException("size must be >= 1")

    - public int offset() : int
      Returns page * size (firstResult for JPA). Used by all paginated queries.

 3) repository.GenericRepository<T>  [src/main/java/com/backend/repository/GenericRepository.java]
    Purpose: Shared CRUD for all entities. UUID is hard-coded as ID type because
             Task 01 mandates UUID for every entity; no generic <ID> needed.

    Fields:
      protected final EntityManager em
      protected final Class<T> entityClass

    - public GenericRepository(EntityManager em, Class<T> entityClass)
      Constructor — borrows EM (never creates/closes), stores target class.

    - public Optional<T> findById(UUID id) : Optional<T>
      em.find(entityClass, id) wrapped in Optional.ofNullable. Proxy-safe.

    - public List<T> findAll(Pageable pageable) : List<T>
      Criteria API: cb.createQuery(entityClass), cq.select(cq.from(entityClass)), setFirstResult(offset)/maxResults(size).

    - public T create(T entity) : T
      em.persist(entity); return entity. Requires active transaction outside repo.

    - public T update(T entity) : T
      return em.merge(entity). Works for detached instances.

    - public void delete(T entity) : void
      em.remove(em.contains(entity) ? entity : em.merge(entity)) — merges first if detached to avoid IllegalArgumentException.

    - public void deleteById(UUID id) : void
      findById(id).ifPresent(this::delete) — no exception if missing.

    - public long count() : long
      Criteria: select(cb.count(cq.from(entityClass))), getSingleResult().

 4) repository.UserRepository extends GenericRepository<User>
    Serves: POST /auth/register (duplicate), POST /auth/login, POST /auth/resend-verification, GET /admin/users
    Constructor: public UserRepository(EntityManager em) -> super(em, User.class)

    - public Optional<User> findByEmail(String email) : Optional<User>

      Used for login lookup.

    - public boolean existsByEmail(String email) : boolean

    - public List<User> search(UserRole role, Boolean verified, Boolean blocked, String searchText, Pageable pageable) : List<User>
      Criteria API with 4 optional filters. Builds Predicate[] via searchPredicates(...), where(cb), orderBy(createdAt DESC), paginated.
      Endpoint: GET /admin/users?role=&verified=&blocked=&search= (search matches fullName OR email, case-insensitive LIKE %text%).

    - public long countSearch(UserRole role, Boolean verified, Boolean blocked, String searchText) : long
      Same predicates as search() but select(cb.count(root)). For paginated envelope totalItems.

    - private Predicate[] searchPredicates(CriteriaBuilder cb, Root<User> root, UserRole role, Boolean verified, Boolean blocked, String searchText) : Predicate[]
      Adds: role==, verified==, blocked== if non-null; if searchText non-blank -> OR( lower(fullName) LIKE %lower%, lower(email) LIKE % ). Returns toArray.

 7) repository.BookingRepository extends GenericRepository<Booking>
    Serves: GET /bookings/mine, GET /bookings/received, overlap check for PATCH /bookings/{id}/status, delete guard DELETE /listings/{id}
    Constructor: public BookingRepository(EntityManager em)

    - public List<Booking> findByVisitor(User visitor, Pageable pageable) : List<Booking>
      JPQL: "SELECT b FROM Booking b WHERE b.visitor = :visitor ORDER BY b.createdAt DESC" paginated. For GET /bookings/mine.

    - public List<Booking> findByListingHost(User host, BookingStatus status, Pageable pageable) : List<Booking>
      JPQL with optional status: "SELECT b FROM Booking b WHERE b.listing.host = :host" + (status!=null ? " AND b.status = :status" : "") + " ORDER BY b.createdAt DESC"
      Uses TypedQuery, conditionally setParameter("status"). For GET /bookings/received?status= (across all host listings).

    - public List<Booking> findOverlapping(Listing listing, LocalDate checkIn, LocalDate checkOut, List<BookingStatus> statuses, UUID excludeBookingId) : List<Booking>
      JPQL: "SELECT b FROM Booking b WHERE b.listing = :listing AND b.status IN :statuses AND b.id <> :excludeId AND b.checkIn < :checkOut AND b.checkOut > :checkIn"
      Half-open interval overlap logic: [a1,a2) overlaps [b1,b2) iff a1<b2 && a2>b1. Same-day turnover (checkout==checkin) is NOT overlap. Backs PATCH /bookings/{id}/status auto-reject: on CONFIRMED, find other PENDING overlapping bookings to reject. Service decides when to call.

    - public boolean existsActiveBookingForListing(Listing listing) : boolean
      JPQL COUNT: "SELECT COUNT(b) FROM Booking b WHERE b.listing = :listing AND b.status IN :statuses" with PENDING,CONFIRMED -> count>0. Guard for DELETE /listings/{id} -> 409 CANNOT_DELETE_WITH_ACTIVE_BOOKINGS.

 DESIGN PATTERNS USED IN TASK 02
 --------------------------------------------------------------------------------
  Yes — 4 deliberate patterns. No accidental pattern bloat.

  1) Repository Pattern (primary pattern for the whole task)
     Definition: Mediates between domain and persistence. Encapsulates
     storage/retrieval/queries, exposes collection-like interface for
     domain objects, hides JPQL/Criteria details. Returns entities only,
     never DTOs (mapping is Task 03).
     Applied: GenericRepository<T> [repository/GenericRepository.java:10]
             as generic collection facade over EntityManager, plus 7
             typed extensions (UserRepository, ListingRepository,
             PhotoRepository, BookingRepository, MessageRepository,
             ReportRepository, RefreshTokenRepository). Each adds only
             the query methods its endpoints need (§6.1-6.7).
             Callers never call em.persist/merge directly.
     Why: Spec §1 layering (Repository → Service). Tests can mock/swap
          repos; queries change in one place.

  2) Singleton — Eager Static Initialization via Utility Class (JpaUtil)
     Definition: Ensure exactly one instance of a resource, globally
     accessible, thread-safe without synchronization.
     Applied: persistence/JpaUtil.java:11-18
             final class, private JpaUtil(){}, private static final EMF
             = buildEntityManagerFactory(), static accessors
             createEntityManager()/shutdown(). EMF built eagerly at
             class-load; JVM guarantees thread-safety. Matches
             persistence-unit "invest-pu" in one place.
     Why: EntityManagerFactory is heavyweight (connection pool + metamodel);
          per JPA spec it must be singleton per app.

  3) Factory Method (Static Factory) + Value Object
     Definition: Creator method manufactures product without exposing
     construction details.
     Applied: JpaUtil.createEntityManager() [JpaUtil.java:143] delegates
             to EMF.createEntityManager(). Callers get a fresh
             EntityManager without knowing Dotenv props or PU name.
             Pageable [repository/Pageable.java:3] is a Value Object /
             Parameter Object record (page, size, offset()) with
             invariant validation — immutable factory for pagination.
     Why: Centralizes creation; Service later can replace with CDI
          @Produces without changing repositories.

  4) Dependency Injection — Constructor Injection + Inversion of Control
     Definition: Dependencies are supplied from outside, not created
     inside. Repositories "borrow" their collaborator.
     Applied: Every repository ctor takes EntityManager exclusively
             (UserRepository(EntityManager em) [UserRepository.java:14],
              ListingRepository etc.), GenericRepository(EntityManager, Class<T>).
             No repo calls new JpaUtil(), Persistence.create..., or
             getTransaction(). Per spec §3.1 borrow-not-own.
     Why: Repo works whether or not a transaction is already open;
          Service controls tx boundary; unit tests can inject a
          test EntityManager (or mock).

  5) Template Method via Inheritance (Generic → Specific)
     Definition: Base class defines skeleton of operations; subclasses
     fill in specializations.
     Applied: GenericRepository defines findById/findAll/create/update/
             delete/count [GenericRepository.java:199-235]; specific
             repos inherit and only override/add searchPredicates or
             JPQL queries. Avoids duplicating pagination and CRUD.
     Why: DRY; 7 repos share identical CRUD without copy-paste.

  Patterns deliberately NOT used:
   - Active Record (entities would manage their own persistence) — avoided
     per spec; entities stay anemic POJOs, repos handle persistence.
   - Service Locator / CDI (@ApplicationScoped/@Inject) — deferred per §0/§7.
   - Unit of Work exposed in repos — transactions stay in Service layer.

 TASK 03 — Transactions, Exceptions & Listing Service
 DarCom Co-Hosting Platform (darcom-backend)
 Stack: Java 21 · Jakarta EE 10 (Persistence 3.1, Validation 3.0) · Hibernate 6.4.4 · PostgreSQL
================================================================================

  Goal: Give the Service layer a real transaction boundary and a way to signal
       spec-defined failures without a Resource layer to catch them yet.
       ListingService covers all six §6 Listings endpoints.

  Deliverable: 7 new files + 2 additive methods in 1 existing file. No tests
               (explicitly out of scope per §0).

 --------------------------------------------------------------------------------
  PURPOSE — WHAT TASK 03 IS FOR, AND WHY IT FOLLOWS 01 AND 02
 --------------------------------------------------------------------------------

  THE SHORT VERSION
    Task 01 built the nouns. Task 02 built the verbs that read and write them.
    Task 03 builds the rules — the layer that decides whether an operation is
    allowed, and that owns the transaction the operation runs in.
    Without it, Tasks 01+02 are a working database access library with no
    business logic anywhere in the project.

  WHERE THE THREE TASKS SIT IN THE SPEC'S LAYERING (§1: Resource -> Service -> Repository)
    +------------------------------------------------------------------+
    |  api/         <-- NOT BUILT YET  (Task 04+)  HTTP, DTOs, auth,     |
    |                 the only layer that knows about status codes,      |
    |                 JSON, bearer tokens, @Valid, exception mappers     |
    +------------------------------------------------------------------+
    |  service/     <-- THIS TASK.  Business rules + transaction         |
    |                 boundary. Knows "is this host allowed to do this?"  |
    |                 and "do these two writes belong in one commit?"    |
    |                 Knows nothing about HTTP.                         |
    +------------------------------------------------------------------+
    |  repository/  <-- TASK 02.  Query construction only.               |
    |                 "listings matching these filters, page N".         |
    |                 Knows nothing about business rules.               |
    +------------------------------------------------------------------+
    |  domain/      <-- TASK 01.  Shape + mapping + invariants.         |
    +------------------------------------------------------------------+
    |  persistence/ <-- TASK 02.  Who owns the EntityManagerFactory.    |
    +------------------------------------------------------------------+

  WHAT TASK 01 GAVE TASK 03 (and it is not re-litigated here)
    - The entities Task 03 operates on: Listing, User, Photo, and the
      ListingStatus enum. TASK-03 §0 explicitly forbids touching domain/** —
      ListingService never adds a field, an annotation, or a validation rule to
      an entity. Business rules live in the service, not smeared into the model.
    - The lazy/eager shape of those entities, which dictates task design:
      every @ManyToOne is LAZY and `activities` is a LAZY @ElementCollection
      (§Task 01). A lazy association read outside a live session throws
      LazyInitializationException. That single fact is why Task 03 needs
      (a) a transaction boundary that stays open for exactly the right amount
      of time, and (b) a fetch strategy for anything handed back to a caller.
      TASK-03 §3.5 (cheap findById vs findByIdWithDetails) and §6.1 are both
      direct consequences of a Task 01 decision, not new preferences.
    - The `equals`/`hashCode` convention (id-based, proxy-safe, `Class.hashCode()`)
      which is what makes `listing.getHost().getId()` safe to call on a lazy
      proxy in delete()'s ownership check.
    - `Listing.setActivities(...)` clear-then-addAll behaviour, which is why
      `update` needs no explicit Hibernate.initialize but `getById` does.
    - hibernate-core, already a dependency — so `Hibernate.initialize(...)` used
      by getById costs nothing new. No pom.xml change in this task.

  WHAT TASK 02 GAVE TASK 03
    - JpaUtil: the single owner of the EntityManagerFactory. Task 03's
      TransactionRunner calls `JpaUtil.createEntityManager()` and is the *only*
      class in service/ that does. Task 02 deliberately shipped with "no
      transaction management (Service layer concern per spec §1)" — that
      concern is exactly what Task 03 now delivers, so the two tasks hand off
      cleanly rather than overlapping.
    - The repository layer, borrowed not owned. Every repository takes an
      EntityManager as a constructor argument and never creates or closes one
      (Task 02 §3.1). That is what makes TransactionRunner possible: it creates
      the EM, hands it to the lambda, and the lambda uses it to `new
      ListingRepository(em)` — the repo has no idea a transaction is happening.
      Had Task 02's repos created their own EntityManagers, the entire
      TransactionRunner design would be impossible.
    - ListingRepository itself. create/getById/search/findMine/update/delete in
      ListingService map almost 1:1 onto existing repo methods: create->create,
      search->search+countSearch, findMine->findByHost, update->update,
      delete->update (soft) + BookingRepository.existsActiveBookingForListing.
      ListingService is mostly orchestration and rules, not new SQL.
    - Pageable, used unchanged as the pagination input to search and findMine.
      Task 02 left size-clamping (max 100) to the Service/Resource layer; this
      task passes it through rather than clamping, so that stays open.
    - The two Task 02 gaps Task 03 had to close. Building a real caller exposed
      that findByHost had no count-side counterpart (countByHost — the same
      search/countSearch pairing already existed for the public search), and
      that no repo method loaded a Listing with its associations fetched
      (findByIdWithDetails — needed the moment a Listing outlives the
      transaction that read it). Both are additive; no Task 02 method was
      renamed, re-signed, or removed.

  WHAT TASK 03 ADDS BACK TO THE PILE
    - TransactionRunner: the missing transaction boundary. It is the one place
      in the whole codebase allowed to call getTransaction(), which is the
      mechanical guarantee that no service method opens a half-finished
      transaction. Every future service (Booking, Message, Report, Auth) reuses
      it unchanged.
    - The ApiException tree: how a layer with no HTTP awareness signals a
      failure. status + errorCode + message are exactly the §1 error envelope,
      so a future ExceptionMapper is pure passthrough with no translation logic.
    - PagedResult<T>: the count-side half of the §1 paginated envelope, generic
      and shared, so Booking/Message/Admin services do not each invent their own.
    - ListingService: the first real business rules in the project — verified
      email to publish, owner-only to edit or delete, no delete while bookings
      are pending/confirmed, soft delete rather than hard.

  THE CONVERSATION THIS TASK HAD TO HAVE FIRST
    There is no Auth layer yet, so nothing can hand a service a "who is calling".
    Task 03 resolves this by having every method that needs the caller take an
    already-resolved `User` (TASK-03 §3.1). ListingService.create(User, Listing)
    is therefore fully callable today; the only missing piece is upstream, and
    it belongs to Task 04+ with the Resource layer. The alternative — stubbing
    a fake auth context — would have been a layer that had to be thrown away.

  WHAT THIS TASK DELIBERATELY DID *NOT* DO
    It stopped at the service layer. No DTOs, no JAX-RS resources, no exception
    mapper, no CDI annotations, no JWT parsing, no ValidationException/400, no
    services other than Listing, no photo endpoints, no tests. Every one of
    those is either blocked on a missing prerequisite (storage backend for
    photos, a Resource layer for DTOs and mappers) or is a Resource-layer
    concern (400s via @Valid, HTTP status knowledge). Building them here would
    have meant building things twice.

 1) exception.ApiException  [src/main/java/com/backend/exception/ApiException.java]
    Purpose: One base for every spec-defined failure a service throws. Carries
             exactly the three fields a future JAX-RS ExceptionMapper needs to
             build the §1 error envelope, with zero translation logic.

    - public abstract class ApiException extends RuntimeException
      Abstract on purpose: there is no such thing as throwing one without a
      status, so the base can never be instantiated directly.

    Fields (both final, set once in the ctor):
      private final int status
      private final String errorCode

    - protected ApiException(int status, String errorCode, String message)
      Calls super(message). Status is supplied by the concrete subclass only.

    - public int getStatus() / public String getErrorCode()
      Read verbatim by whatever eventually catches it.

 2) exception.NotFoundException  [NotFoundException.java]
    - public NotFoundException(String errorCode, String message) -> super(404, ...)
    Codes used: LISTING_NOT_FOUND

 3) exception.ForbiddenException  [ForbiddenException.java]

    Codes used: EMAIL_NOT_VERIFIED, NOT_OWNER

 4) exception.ConflictException  [ConflictException.java]
    - public ConflictException(String errorCode, String message) -> super(409, ...)
    Codes used: CANNOT_DELETE_WITH_ACTIVE_BOOKINGS

    Note: each concrete type hardcodes its own status. No constructor anywhere

    once that boundary exists (spec §12); duplicating them here would be a
    second, weaker copy of the same rule.

 5) service.TransactionRunner  [src/main/java/com/backend/service/TransactionRunner.java]
    Purpose: The one place EntityManager + EntityTransaction lifecycle lives.
             Written once instead of in all six service methods.

    - public final class TransactionRunner
      final + private ctor: pure static utility, never instantiated.

    - @FunctionalInterface public interface Work<T> { T run(EntityManager em); }
      Declares no checked exception. Nothing in the EntityManager, repository,
      or exception APIs here throws one, so there is nothing to wrap.

    - @FunctionalInterface public interface VoidWork { void run(EntityManager em); }
      For methods with nothing to return (delete).

    - public static <T> T call(Work<T> work)
      em = JpaUtil.createEntityManager(); tx = em.getTransaction();
      try { tx.begin(); result = work.run(em); tx.commit(); return result; }
      catch (RuntimeException e) { if (tx.isActive()) tx.rollback(); throw e; }
      finally { em.close(); }
      An ApiException thrown inside the lambda is a RuntimeException: it is
      caught, rolls back, and is rethrown unchanged all the way out.

    - public static void execute(VoidWork work)
      call(em -> { work.run(em); return null; }) — same boundary, result discarded.

 6) service.PagedResult  [src/main/java/com/backend/service/PagedResult.java]
    - public record PagedResult<T>(List<T> items, long totalItems)
      Generic, not Listing-specific. The §1 paginated envelope is
      (items, page, size, totalItems, totalPages) and is reused by nearly every
      collection endpoint in the spec. A service computes the two values that
      need the database; page/size are the caller's own, totalPages is pure
      arithmetic, so the eventual envelope builder does that once, generically,
      instead of every service repeating it.

 7) service.ListingService  [src/main/java/com/backend/service/ListingService.java]
    Purpose: Business rules for all six §6 Listings endpoints. Plain stateless
             class, no constructor, no fields, constructed with `new`.

    - public Listing create(User host, Listing listing)          — POST /listings
      1. if (!host.isVerified()) throw ForbiddenException("EMAIL_NOT_VERIFIED", ...)
      2. listing.setHost(host); listing.setStatus(ListingStatus.ACTIVE)
      3. return TransactionRunner.call(em -> new ListingRepository(em).create(listing));
      Steps 1-2 are plain field access/mutation on an object already in memory
      and happen BEFORE any transaction opens. The transaction wraps only persist.

    - public Listing getById(UUID id)                            — GET /listings/{id}
      TransactionRunner.call: findByIdWithDetails(id).orElseThrow(NOT_FOUND),
      then Hibernate.initialize(listing.getActivities()), return the Listing.
      The entity is handed back after the tx commits and the EM closes, so every
      association a caller might read has to already be loaded. activities is
      initialized explicitly rather than fetch-joined (see MultipleBagFetchException
      note in findByIdWithDetails). PUT reuses this exact response shape.

    - public PagedResult<Listing> search(String city, BigDecimal minPrice,
        BigDecimal maxPrice, Boolean mealsIncluded, Pageable pageable)  — GET /listings
      TransactionRunner.call: repo.search(...) for the page, repo.countSearch(...)
      for the total, wrapped in PagedResult. ACTIVE-only is enforced in the
      repository, not here. All four filters optional (null = no filter).

    - public PagedResult<Listing> findMine(User host, Pageable pageable) — GET /listings/mine
      TransactionRunner.call: repo.findByHost(host, pageable) + repo.countByHost(host)
      -> PagedResult. No status filter — the host sees ACTIVE, HIDDEN and REMOVED.

    - public Listing update(User host, UUID listingId, Listing changes) — PUT /listings/{id}
      TransactionRunner.call: findByIdWithDetails -> orElseThrow(NOT_FOUND) ->
      requireOwner(existing, host) -> copy the 9 editable fields (title,
      description, city, address, pricePerNight, currency, mealsIncluded,
      activities) -> repo.update(existing).
      `changes` is a partially-populated detached Listing used purely as a
      carrier for incoming values; it is never persisted. host, status, id and
      createdAt are NOT copyable — status changes only via delete (REMOVED) or
      the §10 block side effect (HIDDEN).
      No Hibernate.initialize on activities: Listing.setActivities() calls
      clear() first, and that clear() is itself what forces Hibernate to load
      the about-to-be-discarded old collection — which is fine, we are still
      inside the transaction.

    - public void delete(User host, UUID listingId)              — DELETE /listings/{id}
      TransactionRunner.execute: findById -> orElseThrow(NOT_FOUND) ->
      requireOwner -> if (new BookingRepository(em).existsActiveBookingForListing(listing))
      throw ConflictException("CANNOT_DELETE_WITH_ACTIVE_BOOKINGS") ->
      listing.setStatus(ListingStatus.REMOVED); listingRepo.update(listing).
      Soft delete only. Never em.remove.
      Uses the cheap findById, not findByIdWithDetails: the only association it
      touches is listing.getHost().getId(), and Hibernate embeds the FK id in a
      lazy @ManyToOne proxy without a query, so no load is needed. Nothing is
      returned to a caller either, so there is no association left uninitialized.

    - private void requireOwner(Listing listing, User host)
      if (!listing.getHost().getId().equals(host.getId()))
          throw new ForbiddenException("NOT_OWNER", "You do not own this listing")
      Shared verbatim by update and delete rather than duplicated.

 8) repository.ListingRepository — 2 additive methods  [ListingRepository.java]
    Serves: getById (findByIdWithDetails), update (findByIdWithDetails),
            findMine (countByHost)

    - public Optional<Listing> findByIdWithDetails(UUID id) : Optional<Listing>
      JPQL: "SELECT DISTINCT l FROM Listing l JOIN FETCH l.host LEFT JOIN FETCH l.photos
             WHERE l.id = :id" -> getResultStream().findFirst()
      Needed because getById and update both return a Listing to a caller after
      the transaction that loaded it has closed, and §6's GET/PUT response
      includes photos[] and a host summary block. A lazy proxy would throw on
      first touch outside a live session.
      host = inner JOIN FETCH (always present, never null).
      photos = LEFT JOIN FETCH (a listing may legitimately have zero).
      DISTINCT is required: fetch-joining a collection repeats the parent row
      once per child row, so a 3-photo listing would otherwise appear 3 times.
      activities is deliberately NOT fetch-joined — photos is a List (a "bag"),
      and fetch-joining two collections in one query risks
      MultipleBagFetchException. ListingService.getById initializes it separately.

    - public long countByHost(User host) : long
      JPQL COUNT: "SELECT COUNT(l) FROM Listing l WHERE l.host = :host" -> getSingleResult()
      Count-side counterpart to the existing findByHost. GET /listings/mine is
      paginated exactly like GET /listings, so it needs a totalItems just the
      way the existing search/countSearch pair already provides one.

    New imports added: java.util.Optional, java.util.UUID (countByHost needs nothing new).

 --------------------------------------------------------------------------------
  CONVENTIONS ESTABLISHED IN TASK 03
 --------------------------------------------------------------------------------
   1) Services take resolved domain objects, not tokens (§3.1)
      Every method that needs to know the caller takes an already-loaded
      `User`. There is no Auth layer to hand a service a bearer token and none
      is needed — identifying the caller is upstream work, applying the business
      rule is not. ListingService.create(User, Listing) is fully callable today;
      the only missing piece is something that resolves a JWT into that User.

   2) Every public method goes through TransactionRunner (§3.2)
      No service method calls JpaUtil.createEntityManager(), and no repository
      is ever constructed outside a TransactionRunner lambda. A repository needs
      an EntityManager bound to one specific unit of work (Task 02 §3.1) — and
      that unit of work is exactly what TransactionRunner creates and tears down.

   3) Services are stateless (§3.3)
      No constructor, no fields. Each method builds the repositories it needs
      fresh from the `em` its lambda receives. This is also why no wiring is
      needed yet: @ApplicationScoped on a fieldless class is a one-line change
      when CDI shows up, not a redesign.

   4) Failures throw, they don't return a code (§3.4)
      Never null, never a boolean, never a custom result wrapper. Each exception
      carries the exact status + machine-readable error code the §1 envelope
      needs, so the eventual mapper is pure passthrough.

   5) Two ways to look up a Listing, deliberately (§3.5)
      findById (cheap, no joins) for delete, which returns nothing and only
      needs the host's id. findByIdWithDetails (host + photos fetched) for
      getById and update, which hand a Listing back to their caller.

 --------------------------------------------------------------------------------
  DESIGN PATTERNS USED IN TASK 03
 --------------------------------------------------------------------------------
   6) Facade / Template Method (TransactionRunner)
      Definition: A single class owns a multi-step algorithm; callers supply
      only the varying step via a callback.
      Applied: TransactionRunner.call(Work<T>) / execute(VoidWork) own the
               fixed sequence (create EM -> begin -> run -> commit | rollback ->
               close). The Work/VoidWork functional interfaces are the varying
               step, supplied as a lambda by each service method. Rollback and
               close are inherited by every caller for free and cannot be
               forgotten at a call site.
      Why: Six service methods all need the same envelope. Written once, the
           transaction boundary is now impossible to get subtly wrong in one
           method and right in another.

   7) Null Object / Sentinel via Exception-as-Control-Flow (ApiException hierarchy)
      Definition: A condition that is a normal, expected outcome of the domain
      (not found, not owner, conflict) is signalled by a typed object carrying
      the data needed to respond, rather than by a return value every caller
      must remember to check.
      Applied: The 4-class ApiException tree. Each instance carries status +
      errorCode + message, so the failure travels intact from the throw site to
      whatever catches it without any intermediate branching.
      Why: Spec §1 requires a single error envelope. Encoding the response data
           in the exception removes the possibility of a call site inventing its
           own error shape, and makes the business rule (this host doesn't own
           this listing) legible in the source.

   8) Inversion of Control (Work<T> callback)
      Definition: A component's control flow is inverted — it calls back into
      code it was handed instead of hardcoding a collaborator.
      Applied: TransactionRunner has no knowledge of any repository. It hands
               an EntityManager to a lambda and waits.
      Why: Keeps the transaction infrastructure unaware of the domain, so it
           stays reusable for BookingService, MessageService, AuthService, etc.
           unchanged.

   Patterns deliberately NOT introduced:
    - Service Locator / static singleton service instance — ListingService is
      `new`'d like Task 02's repositories; CDI comes later as a one-line change.
    - Result/Wrapper return type (e.g. a Result<T> instead of PagedResult for
      errors) — would duplicate what the exception tree already expresses, and
      would force every call site into a match/if.

 --------------------------------------------------------------------------------
   (Note: API-Specification.md itself is not in the repo — these are read off the

   1. §6 shows "a host summary block" for GET /listings/{id} but never lists
      which host fields it contains.
      Resolution: did not guess. getById returns the whole Listing with host
      eagerly fetched; picking a subset of host fields is a DTO decision, and
      DTOs are explicitly out of scope (§8). The Resource layer narrows it.

   2. §6 does not say whether GET /listings/{id} should 404 for a REMOVED or
      HIDDEN listing. search() is ACTIVE-only, so those listings already vanish
      from the public list, but getById has no status filter at all and will
      return one to any caller who knows the id.
      Resolution: followed TASK-03 §7 literally — no status filter. This is the
      one behaviour I'd most want a second opinion on before the Resource layer
      ships: probably non-ACTIVE listings should be visible to the owner and
      404 for everyone else, which is a check the service or the resource will
      need. Flagged, not silently changed.

   3. §6 does not say whether PUT /listings/{id} is allowed to change status.
      Resolution: treated as no. status, host, id and createdAt are not among
      the 9 fields update() copies; status is only ever written by delete()
      (REMOVED) or the §10 block side effect (HIDDEN). That keeps a host from
      un-hiding a listing removed by an admin by round-tripping PUT.

   4. §6's paginated envelope is (items, page, size, totalItems, totalPages) but
      PagedResult carries only items + totalItems.
      Resolution: intentional. page and size are the caller's own inputs, and
      totalPages is arithmetic on totalItems/size — neither needs the database,
      so neither belongs in a repository-backed result. The envelope builder
      will add them once, generically.

   5. §6's PUT semantics ("full replace") vs. a partial PATCH.
      Resolution: PUT is implemented as a full replace of the editable fields,
      exactly as TASK-03 §7 specifies. A PATCH would need null-vs-absent
      distinction, which a partially-populated entity cannot express; that needs
      a DTO, so it stays out of scope.

  THE SHORT VERSION
    Tasks 01–03 built a system that can store users and enforce rules about
    them — but with no way to tell users apart at the door. Every service
    method takes "an already-resolved User" (Task 03 §3.1) and until now that

    on purpose — it issues tokens but nothing reads one back yet, because the

    - The consumer side of auth itself. Task 03 §3.1 said "every method takes an
      already-resolved User... the only thing missing is something upstream that
      resolves a JWT into that User." Task 04 builds the producer side — but
      deliberately only the issuing half. The resolving half (verify/parse) is

  WHAT TASK 04 ADDS BACK TO THE PILE
    - PasswordHasher: the project's only password code, behind a two-method API
      that makes the wrong thing (comparing strings) unexpressible at call sites.
    - JwtService: the issuing half of token auth, with the key discipline
      (eager load, fail loud on weak keys, minimal claims, strongest-HMAC
      selection) baked in so no later caller can get it wrong.
    - RefreshTokenHasher: the split-knowledge half — raw for the wire, hash for
      the disk — with the fast-hash/slow-hash choice documented at the call site.
    - AuthService: the first code in the project that mints identity. Every
      future protected endpoint's filter will resolve against exactly the rows
      and tokens this service writes.
    - UnauthorizedException: completes the status family (401/403/404/409) —
      there is now no HTTP error class the service layer needs that it lacks
      short of the 400 that belongs to @Valid at the boundary.

  THE PROBLEM THIS TASK HAD TO SOLVE FIRST
    A token system has two halves — minting and checking — and the natural
    instinct is to build both. But checking a bearer token means turning it
    into a User on every request, which needs a home (a JAX-RS filter in front
    of protected endpoints) that cannot exist before the Resource layer. So
    Task 04 issues only, and JwtService has no verify/parse method — the same
    reasoning as Task 03's "no fake auth context": a verification method with
    no caller would be speculative code rotting until Task 05+, or worse, two
    competing verification paths when the real one arrives. The task says what
    the follow-up is (§8: "a small, natural follow-up when that task arrives")
    instead of pre-building it.

  WHAT THIS TASK DELIBERATELY DID *NOT* DO
    It stopped at issuing. No verify/parse, no email verification or password
    reset (no provider chosen — same blocker as Task 03's photos), no rate
    limiting (called out as a real production gap, §0/§8, not silently absent),
    no DTOs, no resources, no mapper, no CDI, no tests. The rate-limiting note
    deserves emphasis: it is the first deferred item in this project that is a
    live vulnerability rather than missing functionality, and the task marks it
    as such instead of burying it.

 1) exception.UnauthorizedException  [exception/UnauthorizedException.java]
    - public UnauthorizedException(String errorCode, String message) -> super(401, ...)
    Same shape as Task 03's other three, same package. None of Listing's errors
    needed a 401 (NOT_OWNER is 403, LISTING_NOT_FOUND is 404, the delete guard
    is 409) — auth is the first thing that genuinely does: wrong credentials
    and a bad refresh token are "you are not authenticated," not "you're
    authenticated but not allowed."
    Codes used: INVALID_CREDENTIALS, INVALID_REFRESH_TOKEN

 2) security.PasswordHasher  [security/PasswordHasher.java]
    Purpose: The only place a raw password is ever touched — and even here it
             is never stored, logged, or returned. char[]-based API so the raw
             password doesn't linger as an immutable String.

    - private static final int COST = 12  (2^12 rounds; revisit upward as hardware improves)
    - public static String hash(String rawPassword)
      BCrypt.withDefaults().hashToString(COST, rawPassword.toCharArray())
    - public static boolean matches(String rawPassword, String hash)
      BCrypt.verifyer().verify(rawPassword.toCharArray(), hash).verified
    Known bcrypt trap (worth knowing, not a concern): the algorithm only looks
    at the first 72 bytes — anything beyond is silently ignored in both hash
    and verify. Only matters if register ever gets a max-length rule.

 3) security.RefreshTokenHasher  [security/RefreshTokenHasher.java]
    Purpose: Raw token for the client, hash for the DB — the split Task 01
             built RefreshToken.tokenHash for. If the table leaked, no row in
             it is usable as a bearer token.

    - private static final SecureRandom RANDOM = new SecureRandom()
    - public static String generateRaw() — 64 SecureRandom bytes, base64url, no padding.
      What goes to the client. Never stored as-is.
    - public static String hash(String rawToken) — SHA-256, hex-encoded. What
      RefreshToken.tokenHash actually stores. SHA-256-not-bcrypt on purpose:
      bcrypt's slowness is the point for low-entropy human passwords; a refresh
      token is already 64 unguessable bytes, so an adaptive hash buys nothing
      and only costs CPU on every refresh/logout. (NoSuchAlgorithmException is
      wrapped in IllegalStateException but can never fire — SHA-256 is mandatory
      on every JVM per the JCA spec.)

 4) security.JwtService  [security/JwtService.java]
    Purpose: Issues signed access tokens. Nothing parses one back yet — that
             belongs to whatever resolves a bearer token into a User, which
             doesn't exist until the Resource layer does (§8).

    - private static final Duration ACCESS_TOKEN_TTL = Duration.ofMinutes(15)
    - private static final SecretKey KEY = loadKey() — static-eager-init, same
      shape as JpaUtil (Task 02): one key, loaded once at class-load. If
      JWT_SECRET decodes to <32 bytes, Keys.hmacShaKeyFor throws WeakKeyException
      immediately — loud failure at first touch, never a silently weak key.
    - private static SecretKey loadKey() — Dotenv JWT_SECRET -> BASE64 decode ->
      Keys.hmacShaKeyFor. Same Dotenv pattern JpaUtil uses.
    - public static String issueAccessToken(User user)
      sub = user id, claim "role" = role name, iat + 15-min exp,
      .signWith(KEY).compact(). Single-arg signWith lets JJWT pick the strongest
      HMAC the key qualifies for (HS512 for our 64-byte key) — hardcoding HS256
      would throw away strength for nothing.
      Deliberately minimal claims: the payload is base64, not encrypted — email,
      name, phone stay out; a caller needing them looks up by the resolved id.

 5) service.AuthResult  [service/AuthResult.java]
    - public record AuthResult(String accessToken, String refreshToken, User user)
    The shape login and refresh both return. `user` is safe to read after the
    transaction closes — User has no associations of its own (Task 01: zero
    collections by design), so once one field is touched in-tx the row is loaded.

 6) service.AuthService  [service/AuthService.java]
    Purpose: Business rules for the four §4 endpoints. Stateless, no fields,
             constructed with `new` — follows Task 03 §3 conventions exactly.

    - public User register(User newUser, String rawPassword)   — POST /auth/register
      1. Role check BEFORE any transaction (plain field check on an in-memory
         object — same reason ListingService.create checks isVerified() outside
         one): HOST or VISITOR only, else ForbiddenException("INVALID_ROLE").
         Rejecting ADMIN self-registration lives in the service on purpose —
         it's a privilege-escalation guard on a public unauthenticated endpoint,
         not a data-shape check, so it isn't left to a @Valid annotation someone
         could forget later.
      2. TransactionRunner.call: existsByEmail -> ConflictException
         ("EMAIL_ALREADY_EXISTS") rather than catching a DB unique violation, so
         the error is clean instead of a leaked SQL exception.
      3. setPasswordHash(PasswordHasher.hash(rawPassword)); setVerified(false);
         setBlocked(false); create. The caller passes a raw password in and a
         persisted User out — the hash is the only password-derived thing that
         ever reaches the database.
      Returns just the created User — NO tokens. See the §10 flag below.

    - public AuthResult login(String email, String rawPassword)  — POST /auth/login
      TransactionRunner.call: findByEmail -> orElseThrow(Unauthorized,
      "INVALID_CREDENTIALS"); PasswordHasher.matches else the SAME
      Unauthorized/INVALID_CREDENTIALS (§3.4 — checked in this order so neither
      branch leaks whether the email is registered); user.isBlocked ->
      ForbiddenException("ACCOUNT_BLOCKED"); issue access token + refresh token
      (persisted hashed via issueRefreshToken); return AuthResult.
      Note the ordering: blocked is checked AFTER credentials, so a blocked
      account still can't be distinguished from a bad password without knowing
      the right one.

    - public AuthResult refresh(String rawRefreshToken)  — POST /auth/refresh
      TransactionRunner.call: hash the presented token, findByTokenHash ->
      orElseThrow(Unauthorized, "INVALID_REFRESH_TOKEN"); if expired, DELETE it
      then throw Unauthorized/INVALID_REFRESH_TOKEN (an expired token is cleaned
      up as it's rejected); else delete the presented token (rotation: single-use,
      §3.3) and issue a fresh access + refresh pair. Delete + re-issue happen in
      the SAME transaction — a crash between them can't leave both valid or
      neither. A leaked token is only good until the holder's next refresh.

    - public void logout(String rawRefreshToken)  — POST /auth/logout
      TransactionRunner.execute: hash + deleteByTokenHash. Never throws — an
      unknown or already-used token ends in the identical state (that token
      doesn't work), so there's nothing worth reporting.

    - private String issueRefreshToken(EntityManager em, User user)
      generateRaw -> new RefreshToken(user, hash(raw), now+30d) -> create ->
      return raw. TTL: 30 days.

    Error codes emitted: INVALID_ROLE (403), EMAIL_ALREADY_EXISTS (409),
    INVALID_CREDENTIALS (401), ACCOUNT_BLOCKED (403), INVALID_REFRESH_TOKEN (401).
    Nothing else — no ad-hoc RuntimeException anywhere in the throw paths.

  CONVENTIONS — TASK 04 ADDS FOUR, INHERITS THE REST FROM TASK 03
 --------------------------------------------------------------------------------
   New (§3.1–3.4):
   1) Passwords are never compared directly — always PasswordHasher.matches,
      never .equals on a raw string or a hash.
   2) Client sees the raw refresh token; the DB only ever sees its hash.
      One-way SHA-256, no recovery operation exists by design.
   3) Refresh is rotation, not reuse — presented token deleted + new one issued
      in the same transaction. Single-use by construction.
   4) Login never distinguishes "no such account" from "wrong password" —
      identical INVALID_CREDENTIALS either way, so the endpoint doesn't leak
      which emails are registered.
   Inherited (Task 03 §3, §3.5): TransactionRunner for every method, stateless
   service with repos built fresh in the lambda, typed-exception failures only.

 --------------------------------------------------------------------------------
  DESIGN PATTERNS USED IN TASK 04
 --------------------------------------------------------------------------------
   9) Token Rotation (refresh)
      Definition: A credential is single-use — presenting it consumes it and
      mints a successor in the same atomic step.
      Applied: AuthService.refresh deletes the presented RefreshToken row and
               persists its replacement inside one TransactionRunner.call.
      Why: Bounds the blast radius of a leaked token to "until the legitimate
           holder's next refresh," with no revocation list to maintain.

   10) Hash-Separation / Split Knowledge (refresh tokens)
      Definition: The bearer value and the stored verifier are different
      objects; the store alone is insufficient to impersonate.
      Applied: Raw token (base64url, to the client) vs SHA-256 hex (in
      RefreshToken.tokenHash). Same idea as password hashing, tuned
      differently — fast hash because the input already has 512 bits of entropy.
      Why: A read-only DB leak yields zero usable sessions.

   11) Fail-Closed Static Initializer (JwtService.KEY)
      Definition: Security-critical configuration is validated eagerly at
      load time so misconfiguration is impossible to ship silently.
      Applied: KEY is loaded once at class-load; a short/weak JWT_SECRET throws
               WeakKeyException on first touch instead of signing weak tokens.
      Why: Mirrors JpaUtil's eager EMF build — the same "find out loudly at
           startup, not quietly in production" philosophy Task 02 chose.

   Patterns deliberately NOT introduced:
    - Strategy/chain for credential checking (password vs token vs OAuth) —
      two mechanisms, one class, no abstraction needed yet.
    - Observer/event for "on login" side effects (last-login timestamp, audit
      log) — no such column or table exists; not inventing one.

 --------------------------------------------------------------------------------
  DESIGN PATTERNS USED IN TASK 05
 --------------------------------------------------------------------------------
   12) Front Controller + Filter Chain (Jersey/servlet)
      Definition: One entry point owns dispatch; orthogonal concerns attach as
      ordered filters around the endpoint invocation.
      Applied: RestApplication (front controller, @ApplicationPath) +
               AuthenticationFilter at Priorities.AUTHENTICATION (chain link).
               The priority is set correctly with one filter registered so the
               second one never needs a retrofit.
      Why: Auth becomes ambient — no resource method will ever parse a header.

   13) Provider / ExceptionMapper (JAX-RS)
      Definition: Failure rendering is registered capability, not call-site code.
      Applied: ApiExceptionMapper (typed) + GenericExceptionMapper (catch-all);
               JAX-RS picks most-specific, so ApiException never reaches the
               generic one. Filter throws into the same pipeline (§3.4).
      Why: One wire shape for every error, present and future, with zero
           per-resource try/catch.

   14) SecurityContext as Request-Scoped Identity Carrier
      Definition: The container's own per-request slot carries caller identity
      from authentication to authorization to the endpoint.
      Applied: Filter sets UserSecurityContext; RolesAllowedDynamicFeature reads
               isUserInRole; resource reads getUser(). Three consumers, one object,
               standard interface — no project-global "current user" static.
      Why: No statics, no thread-locals, no second lookup; the standard slot the
           framework already passes everywhere.

   Patterns deliberately NOT introduced:
    - DTO/assembler for the diagnostic response — a 3-field record is not a layer.
    - Custom authorization annotations — @RolesAllowed already exists; wrapping it
      would be novelty for its own sake.
    - A logging facade — one log statement doesn't justify one.

  DEPLOY DEVIATIONS (§10.4) — WHAT DIDN'T MATCH THE TASK FILE'S ASSUMPTIONS
 --------------------------------------------------------------------------------
   Two, both required, both minimal, both compile-clean against §9:

   D1. WhoAmIResource injection point (§8 verbatim doesn't work on Jersey).
       Symptom: ClassCastException — SecurityContextInjectee cannot be cast to
       UserSecurityContext; every authenticated call -> 500 via GenericExceptionMapper.
       Cause: Jersey wraps an @Context-injected SecurityContext in its own delegate;
       the "one cast" from §5.2's javadoc only holds for the instance the filter
       set. Fix: resource takes @Context ContainerRequestContext and calls
       getSecurityContext() (portable JAX-RS API, returns the raw instance) —
       same one-cast contract, no Jersey-internal dependency. Diagnostic-only file;
       production classes untouched by this. Documented in the file's javadoc.

   D2. GenericExceptionMapper ate framework statuses (§6 verbatim incomplete).
       Symptom: VISITOR on host-only -> 500, not the task's own "403 if VISITOR".
       Cause: a registered ExceptionMapper<Throwable> outranks Jersey's default
       handling, so RolesAllowed's ForbiddenException (which carries its own 403
       Response) was flattened to 500. Fix: `if (exception instanceof
       WebApplicationException) return exception.getResponse();` first — 4 lines,
       framework statuses pass through, truly-unexpected still becomes 500.
       Same fix also preserves future 404s. Noted in the file's javadoc.

   Consequence to record: the 403 body is Tomcat/Jersey's default HTML error
   page, NOT the JSON envelope — status is correct per §10, shape is not the
   envelope. Giving 403s the envelope would need an ExceptionMapper<Forbidden-
   Exception> with an invented error code — that is the "finer-grained response"
   product decision §0 defers, so it stays deferred. Flagged, not snuck in.

 --------------------------------------------------------------------------------
  DESIGN PATTERNS USED IN TASK 06
 --------------------------------------------------------------------------------
   15) Boundary Object / DTO (§3.1–§3.2)
      Definition: Distinct types for crossing a layer boundary, decoupled from
      the domain's shape and lifecycle.
      Applied: Request beans (validation + Jackson-in) vs records (Jackson-out)
               vs entities (JPA) — three shapes for one concept, each owned by
               its layer. from() factories are the single crossing point.
      Why: API shape can evolve without touching tables; passwordHash can never
           leak because it has no field to leak through.

   16) Thin Adapter (AuthResource, §3.3)
      Definition: A layer whose only job is translating between its neighbors'
      protocols, containing no domain logic.
      Applied: DTO->User/String->service->DTO; status codes are the only
               decisions made here. §9.6 grep is the mechanical enforcement.
      Why: Business rules stay in one testable place; adding ListingResource
           later is mapping work, not rule work.

   17) Provider-Based Cross-Cutting Validation (§5 + jersey-bean-validation)
      Definition: A framework extension point applies a concern uniformly,
      without call-site code.
      Applied: @Valid annotations + auto-discovered BV feature + explicitly
               registered mapper. Zero validation code in AuthResource.
      Why: Every future @Valid gets the same 400 envelope for free.

   Patterns deliberately NOT introduced:
    - A generic DTO<->entity mapper (ModelMapper/MapStruct style) — from() per
      DTO is explicit and total; reflection mapping hides the field list that
      IS the security mechanism here.
    - A ValidationException type — would require catching CVE just to rethrow,
      pure ceremony (§4).

   18) Eager-Boundary Initialization (companion §§4–5)

      it, each by the mechanism the query shape allows.

      carry them.

               because there is no field to put it in — enforced by absence, and
               absence can't be forgotten like a check can.

           hold structurally beat properties that hold by vigilance.

   CANNOT_BOOK_OWN_LISTING (host==visitor id check) → DATES_UNAVAILABLE
   (overlap vs CONFIRMED only — PENDING overlaps allowed, that's what
   auto-reject is for) → persist PENDING → optional first Message
   (visitor→host, same tx) → return booking. Plain findById suffices: em.find
   loads the scalars any future DTO needs; host FK proxy is enough for the
   checks and the message receiver.
 - getById(currentUser, bookingId): WithDetails + three-way viewer check
   (visitor id / listing-host id / ADMIN role) else NOT_AUTHORIZED. Id
   comparisons never load beyond the fetched graph (§3.4 holds: host id rides
   the lazy proxy safely).
 - findMine / findReceived(host, status?, pageable): items + matching count →
   PagedResult. Status filter mirrors the repo's nullable pattern.
 - updateStatus(host, bookingId, newStatus): NOT_LISTING_HOST → narrow to
   CONFIRMED/REJECTED (CANCELLED rejected BEFORE the machine — §3.1: passing
   the machine ≠ authorized) → canTransitionTo → set+update → on CONFIRMED,
   reject every other overlapping PENDING in the SAME tx (all-or-nothing with
   the confirm). Returns the confirmed booking.
 - cancel(visitor, bookingId): NOT_BOOKING_OWNER → machine→CANCELLED else
   INVALID_STATUS_TRANSITION. Visitor-only; host path can't reach CANCELLED.

 Error codes emitted: INVALID_DATE_RANGE, LISTING_NOT_FOUND (reused),
 LISTING_NOT_ACTIVE, CANNOT_BOOK_OWN_LISTING, DATES_UNAVAILABLE,
 BOOKING_NOT_FOUND, NOT_AUTHORIZED, NOT_LISTING_HOST (×2 paths: status + cancel
 use their own), INVALID_STATUS_TRANSITION (×3 paths), NOT_BOOKING_OWNER.
 Types: Conflict/NotFound/Forbidden only — the four-type family scales to a
 third domain without growing (§3.3 confirmed live: no Unauthorized needed).

 --------------------------------------------------------------------------------
  DESIGN PATTERNS USED IN TASK 08
 --------------------------------------------------------------------------------
   20) Saga-Step Atomicity / All-or-Nothing Side Effects (auto-reject)
      Definition: A primary state change and its triggered consequences commit
      or roll back as one unit — no observable intermediate state.
      Applied: confirm + N rejections inside a single TransactionRunner.call.
      Why: A crash between confirm and rejects would leave overlapping PENDINGs
           against a CONFIRMED booking — the exact inconsistency the workflow
           exists to prevent.

   21) Capability Narrowing Before Legality (updateStatus ordering)
      Definition: Check whether the caller may request this *kind* of action
      before checking whether the action is *valid* on the object.
      Applied: CONFIRMED/REJECTED-only gate runs before canTransitionTo.
      Why: Error precedence is information design — "not your action" must win
           over "not a legal move," or callers learn machine details about
           actions they can never perform.

   Patterns deliberately NOT introduced:
    - A booking-state observer/event for auto-reject — the loop is three lines
      in the same transaction; an event bus would add failure modes to the one
      place demanding atomicity.
    - A separate availability service — one predicate call, not a layer.
